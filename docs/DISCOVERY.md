# Local device discovery

With the launcher's **Also check local devices with ICMP** setting enabled, scans check for adjacent upstream paths between saved routers. The local gateway and the upstream router must already be on the map as routers. Each scan can trace up to four saved private router addresses outside the directly attached subnets, with two hops per trace. NetWatch proposes an **Observed upstream route** when hop one matches the local gateway and hop two matches the destination. A saved link stays visible after switching networks. A two-hop trace shows routing order and cannot identify the physical uplink.

If a neighbor at another IP has the same MAC address as a previously discovered default gateway, NetWatch shows **Likely router · Matches known gateway**. To establish that match, scan from each network using the same NetWatch host and retain its discovery records. Routers with separate LAN and uplink MAC addresses need other evidence. New matched devices are added as routers.

A scan reads the Windows route table and shows **Router · Default gateway** even when the gateway is absent from the neighbor table. **Add all to map** adds pending results from the latest successful scan across all pages. It reuses existing map addresses and saves the batch in one inventory update. Clients can link to a gateway added in the same batch.

Discovery is an opt-in convenience for reviewing Windows neighbor-table entries on the host's directly attached private IPv4 networks. Set `NETWATCH_DISCOVERY=1` to enable scheduled scans (five-minute interval); it is off by default. The collector runs the built-in `arp.exe -a` directly with shell execution disabled and literal arguments. This works without a PowerShell script or execution-policy change. Neighbor parsing uses the IPv4 and MAC columns across locales, skips incomplete or invalid entries, and ignores broadcast and multicast MACs. Default gateways are read from the numeric columns of `route.exe print -4`. Optional ICMP sweep is separately disabled by default and enabled with the launcher's ICMP discovery checkbox (`NETWATCH_DISCOVERY_ICMP=1`). It uses the shared eight-permit probe gate and fixed Windows probe helper. Scans are capped at 1,022 addresses; subnets wider than /24 are refused by default and a local `NETWATCH_DISCOVERY_MAX_PREFIX` setting can widen the allowed prefix down to /16, still subject to the sweep cap. No switch or router configuration is needed.

The host derives subnets from active non-loopback, non-link-local RFC1918 IPv4 interfaces and filters neighbor entries to those directly attached ranges. Results have a separate SQLite table and are shown in Discovered devices. Add to draft requires an explicit action and current inventory revision. Review and apply the draft in Edit map. New devices start with monitoring off. Discovery errors preserve prior results. A device becomes Not seen after three successful scans omit it.

The scan includes the host's own MAC from its local network adapter because its own address may be absent from the Windows ARP table.

When adding or updating a discovered device, NetWatch checks the local IPv4 route table. A device matching its subnet's default gateway is typed as a router (including correcting an already-added switch); other devices without a switch port match get a `Gateway route` link when that gateway matches a saved router address. This is a logical next-hop hint, not a verified physical connection; switch-port topology requires separately configured LLDP/SNMP evidence. If the route cannot be read or no saved router matches, the device is added without a link.

For up to 128 results per scan, NetWatch may make bounded reverse-DNS lookups (600 ms each, four concurrent) and display a name hint. A simple hostname match may suggest Router, Switch, Phone or PC; these labels are guesses from names, not device fingerprinting or verified hardware types. DNS may provide no name or a misleading one, so Unknown is expected. Port scans, operating-system fingerprints, SNMP and vendor/OUI lookup are not part of this feature.

The loopback-only API provides `GET /api/v1/discovered?after=0&limit=100`, bodyless `POST /api/v1/discovered/scan-now` and `POST /api/v1/discovered/clear`, and `POST /api/v1/discovered/:id/{add-to-map,remove}`. Write requests require the per-launch `X-NetWatch-Write` token documented in [HOST-API.md](HOST-API.md); add-to-map includes `baseRevision` and uses the existing inventory conflict check. Remove and Clear delete discovery records only; they never delete saved map devices. Results are paginated (maximum 200). The v5 migration is transactional; discovery rows are retained for 30 days and included in SQLite backups. Health and snapshot routes expose scan phase/progress, duration, counts and safe diagnostic codes. A future scan can recreate a removed record if the device is found again.

This method cannot see every device. Wi-Fi client isolation, sleeping devices, randomized phone MAC addresses, and devices on other subnets or VLANs can hide or confuse entries. The neighbor table may contain only recently communicating devices. Treat names and addresses as untrusted hints. Do not treat discovery as authorization or as proof that a device is up or down.

Validation in this branch uses synthetic interfaces and fake neighbor output only. A real Windows home-network comparison remains unverified and must be performed by the owner on the approved network.

## Switch port matches

Save the managed switch as a switch using its management IP, enroll it for read-only SNMPv3 port polling, and run discovery. When the scan has an IP-to-MAC match and one enrolled switch reports that MAC on a port with only that learned address, Discovered devices shows the switch and its interface name. NetWatch records a **Last seen on** hint for review for devices already on the map. **Add to draft** and **Add all to draft** include available connection hints in the draft. When adding devices without a port match, the existing gateway lookup still applies.

When an LLDP chassis MAC matches a discovered address, NetWatch can link the adjacent peer and show both port identifiers. Other MACs learned on that LLDP port are excluded as direct attachments. To locate their access ports, save and enroll the downstream switch as well. SNMP polls retry linking recently scanned devices already added to the map.

The read-only SNMPv3 view must include the bridge-port to interface mapping and the forwarding table. NetWatch checks Q-BRIDGE-MIB first and falls back to BRIDGE-MIB when the VLAN-aware table returns no entries. It uses the table visible to the configured SNMPv3 context. A missing, incomplete, expired, or ambiguous observation supplies no new link. A saved label records the last match, which can still be a port leading to an unmanaged device or downstream switch.

## Review LLDP topology proposals

Enable SNMP port checks on the Windows host and enroll the router or switch you want to start from. Open **Discovered**, choose an enrolled **Start device**, and select **Find connections**. NetWatch reads each enrolled router or switch reached through LLDP within the configured private scope. Devices without enrollment can appear in the results with the reason they were skipped.

Compare the proposed ports and the reporting devices. Use **Review all verified** or review one proposal at a time. Confirm a suggested match by address when the saved device has no chassis identity. Use **Edit map → Use this map → Confirm replacement** to put the reviewed draft into service. New devices start with checks off. These runs start only when an admin requests them.

See the [host API](HOST-API.md#topology-discovery-runs) for enrollment scope, bounds, and the backup required before upgrading to SQLite v12.

For a switch that uses a named SNMPv3 context, open **Port monitoring…** in the Windows launcher while the host is stopped. Select the switch and enter its **VLAN context**. Save it during enrollment or with **Save context**. Leave the field blank to use the default context. Standalone hosts can set `NETWATCH_SNMP_PORT_CONTEXTS` before starting NetWatch. Use comma-separated `management-IP=context-name` entries, for example `192.0.2.2=vlan-100`. Use the exact context spelling reported by the switch. The existing SNMPv3 account needs read access to the bridge-port map and forwarding table in that context. Only enrolled switches use these entries, and regular interface and LLDP polling continue in the default context.

When Cisco Discovery Protocol (CDP) is visible to the switch's default SNMPv3 read view, NetWatch uses the adjacent device's advertised address and interface as a connection hint. It excludes forwarding-table MACs on the same local interface from direct-attachment suggestions. The read view needs the Cisco CDP neighbor cache subtree (`1.3.6.1.4.1.9.9.23.1.2.1.1`).
