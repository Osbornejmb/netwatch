# Local device discovery

Discovery is an opt-in convenience for reviewing Windows neighbor-table entries on the host's directly attached private IPv4 networks. Set `NETWATCH_DISCOVERY=1` to enable scheduled scans (five-minute interval); it is off by default. The collector reads `arp.exe -a` with shell execution disabled and literal arguments. Optional ICMP sweep is separately disabled by default and enabled with the launcher's ICMP discovery checkbox (`NETWATCH_DISCOVERY_ICMP=1`). It uses the shared eight-permit probe gate and fixed Windows probe helper. Scans are capped at 1,022 addresses; subnets wider than /24 are refused by default and a local `NETWATCH_DISCOVERY_MAX_PREFIX` setting can widen the allowed prefix down to /16, still subject to the sweep cap. No switch or router configuration is needed.

The host derives subnets from active non-loopback, non-link-local RFC1918 IPv4 interfaces and filters neighbor entries to those directly attached ranges. Results have a separate SQLite table and are shown in Discovered devices. Add to map requires an explicit action and current inventory revision. New map entries have normal monitoring checks enabled; ICMP authorization remains separately off and is never granted by adding a device. Discovery errors preserve prior results. A device becomes Not seen after three successful scans omit it.

When adding or updating a discovered device, NetWatch checks the local IPv4 route table. A device matching its subnet's default gateway is typed as a router (including correcting an already-added switch); other devices get a `Gateway route` link only when that gateway matches a saved router address. This is a logical next-hop hint, not a verified physical connection; switch-port topology requires separately configured LLDP/SNMP evidence. If the route cannot be read or no saved router matches, the device is added without a link.

For up to 128 results per scan, NetWatch may make bounded reverse-DNS lookups (600 ms each, four concurrent) and display a name hint. A simple hostname match may suggest Router, Switch, Phone or PC; these labels are guesses from names, not device fingerprinting or verified hardware types. DNS may provide no name or a misleading one, so Unknown is expected. Port scans, operating-system fingerprints, SNMP and vendor/OUI lookup are not part of this feature.

The loopback-only API provides `GET /api/v1/discovered?after=0&limit=100`, bodyless `POST /api/v1/discovered/scan-now` and `POST /api/v1/discovered/clear`, and `POST /api/v1/discovered/:id/{add-to-map,remove}`. Write requests require `X-NetWatch-Write: 1`; add-to-map includes `baseRevision` and uses the existing inventory conflict check. Remove and Clear delete discovery records only; they never delete saved map devices. Results are paginated (maximum 200). The v5 migration is transactional; discovery rows are retained for 30 days and included in SQLite backups. Health and snapshot routes expose scan phase/progress, duration, counts and safe diagnostic codes. A future scan can recreate a removed record if the device is found again.

This method cannot see every device. Wi-Fi client isolation, sleeping devices, randomized phone MAC addresses, and devices on other subnets or VLANs can hide or confuse entries. The neighbor table may contain only recently communicating devices. Treat names and addresses as untrusted hints. Do not treat discovery as authorization or as proof that a device is up or down.

Validation in this branch uses synthetic interfaces and fake neighbor output only. A real Windows home-network comparison remains unverified and must be performed by the owner on the approved network.
