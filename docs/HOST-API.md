# Local host API and database (2.1)

Current schema is SQLite `user_version=14`. The v13→v14 upgrade adds discovery schedules, topology changes, and redundancy incidents. The v12→v13 upgrade adds interface link evidence. The v11→v12 upgrade adds discovery run and connection hint tables. The v10→v11 upgrade changes the stored inventory format to topology v2 after verifying an offline backup. The v5→v6 migration backfills `latest_check` from the newest timestamp and sequence per device. The v9→v10 migration removes the former operator credential and sessions. Viewer and admin access, inventory, and audit history are preserved.

Requires Node 22.13+ (built-in node:sqlite; Node 22 prints an experimental SQLite warning). No external database server or runtime package is required. This API serves the loopback dashboard and optional authenticated clients on a private network.

## Run and stop

Windows users can alternatively use the [per-user tray app and desktop shortcut](WINDOWS-LAUNCHER.md). It owns the host lifecycle through private IPC, uses a separate persistent data location by default and uses the same loopback default and optional LAN boundary. Open the launcher and click **Start** in a signed-in Windows session.

From the repository: `npm ci`, `npm run build`, `npm start`. On PowerShell with script execution disabled, use `npm.cmd` for each command. Open **http://127.0.0.1:4317** by default. Set `NETWATCH_PORT` to an integer from 1024 through 65535 before launch to use another port. Stop with Ctrl+C before maintenance. The host serves the compiled UI and API from the same origin and binds to 127.0.0.1 by default. NETWATCH_LAN=1 requires a valid HTTPS certificate and key and additionally binds private IPv4 interface addresses and refreshes them every 60 seconds. Remote requests require valid access configuration and a configured admin password. NETWATCH_HOSTNAMES optionally supplies a comma-separated hostname allow-list, which defaults to the machine hostname. Alternate Host headers, unexpected Origin headers and cross-site fetches are rejected. A request with a `localhost` or `[::1]` Host receives HTTP 403 with the configured IPv4 URL. A malformed encoded API ID or static path receives HTTP 400 `request_rejected` with the message `Malformed URL.` No CORS permission is granted. The host serves `index.html` with `Cache-Control: no-store` and fingerprinted build assets under `/assets/` with a one-year immutable cache lifetime. Vite dev and preview remain browser-only workflows. Use the production host for private-network access.

Data defaults to `data/netwatch.sqlite` relative to the working directory. Set NETWATCH_DB to an absolute path to keep data elsewhere. Protect that directory with OS user permissions. The database contains inventory, history, password and session hashes, and audit records. SNMP credentials stay in the separate Windows vault. Local OS processes that can reach loopback have admin access.

## Browser inventory transfer

The host starts with empty inventory. Browser storage remains the editor's working copy, including existing recovery and versioned JSON export/import. This phase uses explicit transfer, not background synchronization. In Backup → Local host storage, Check host reads current metadata. Load host previews replacement of the browser map. Save to host previews replacement of the host inventory, preserving IDs, positions and links; it does not append duplicates. Cancel changes nothing. Export the visible map first to retain a topology backup. Host JSON export is available by loading host then exporting the current map. Migration is disabled while browser storage recovery is paused.

Only App's browser working copy reaches this control; fresh browser and host inventories are empty. Devices added through the editor or discovery start with monitoring disabled. Discovery returns draft changes that require the normal reviewed inventory replacement. Host device monitoring lets an operator explicitly authorize a previously saved device/address, then Save to host applies that choice. New/changed addresses or types and imported backups default to disabled; v1 imports contain no authorization. The optional Windows collector is described in ICMP-COLLECTOR.md. Check host after a conflict; inspect/export/load the newer host copy before deciding whether to replace it. Checking alone does not merge changes. Refresh loses uncommitted monitoring checkbox changes.

The dashboard defaults to saved host inventory and receives snapshots over Server-Sent Events. If the stream is unavailable, it fetches conditional snapshots every eight seconds while retrying the stream. Hidden tabs close the stream or stop polling and resync on return. The browser working copy has no host observation binding. Details allow explicit monitoring changes on the snapshot's saved inventory/revision; a conflict requires refresh and review, with no automatic write retry. The optional Windows ICMP collector writes checks only when NETWATCH_ICMP=1 and per-device opt-in are both set; no observation-write HTTP route exists.

## Versioned API

Existing routes declare access levels in the host route table. Static GETs outside /api/ are public. Health, snapshots and device details are viewer routes. Discovery results and scans, topology editing, and discovery writes require admin access. Loopback keeps admin access without signing in. Remote users need a session for nonpublic routes.

All API responses are JSON with no-store. Errors use `{ "error": { "code": "request_rejected", "message": "..." } }`; conflicts use `revision_conflict`, unexpected failures `internal_error` with a generic message. HTTP 400 covers invalid input, 401 covers missing sessions and invalid credentials, 403 covers admission or authorization failures, and 404 covers missing routes or devices. Revision mismatches use 409, oversized bodies 413, unsupported content types 415, temporary rate limits 429, and unexpected failures 500.

- `GET /api/v1/health`: `{apiVersion:1, ready:true, collector:{state:"disabled", ...}}`. The listener starts only after migrations and retention cleanup succeed. Startup/database failure leaves no ready listener. Collector readiness is independent; disabled/unsupported/degraded collection does not mean devices are down.
- `GET /api/v1/topology`: `{revision:0, updatedAt:"ISO UTC", topology:{schemaVersion:1,nodes:[],edges:[]}, monitoring:{}}`. Stable inventory IDs and v1 topology match the existing export contract; monitoring maps device IDs to booleans and is separate from topology/observations.
  Topology v1 imports remain supported. The editor and host accept topology v2. Both formats support `edge.uplink` with `label`, `source`, and `target`. Each port has a `label` and an interface `index` (positive integer or null). Resolved physical links use the unordered pair of device ID and interface index per end, so parallel links with distinct ports keep separate IDs. Unresolved links remain in inventory. Topology v2 adds optional `edge.role` (`uplink`, `downlink`, `peer`, or `unknown`) and `topology.roots` (distinct saved router IDs). Optional `topology.groups` holds up to 100 records with `id`, `name`, and 2–16 distinct link IDs in `links`. Legacy groups use the existing router-link restrictions. A group with a `protectedDevice` is a reviewed baseline. Each member must be a mapped connection to that device with distinct ports.
Write clients read the 64-character hex token from the `netwatch-write-token` meta tag in the host-served index and send it in `X-NetWatch-Write` for topology PUTs and discovery POSTs. The host rejects the old header value `1` and prior launches’ tokens with HTTP 403. Reload the dashboard after restarting the host before retrying a write.

The token blocks callers that only know the header name or old value. A local process with access to the loopback origin can read the index and obtain the token. Remote clients receive a separate CSRF token after login.

- `PUT /api/v1/topology`: JSON `{source:"inventory", baseRevision:0, topology:{...}, monitoring:{"device-id":false}}`, headers `Content-Type: application/json`, `X-NetWatch-Write: <write token>`. Missing monitoring entries default false. Full replacement, max 5 MiB UTF-8 including envelope. The host replies with HTTP 413 and closes the connection when a streamed body exceeds the limit. Success returns the new GET shape with incremented revision. The database transaction compares baseRevision after taking the write lock; there is no automatic conflict retry. Clients must explicitly choose inventory as source; `source:"sample"` is rejected.
- `GET /api/v1/snapshot`: `{generatedAt:"ISO UTC", collector:{state:"disabled", ...}, freshness:{staleAfterMs:90000}, observations:[]}`. Observation entries are `{deviceId,status:"up"|"down"|"unknown",checkedAt:"ISO UTC",outcome:"reachable"|"unreachable",reason,latencyMs:number|null}`. Raw outcome is separate from the threshold-derived status; see ICMP-COLLECTOR.md. Each device is independent. Missing/invalid/future evidence is unknown; valid evidence older than the host freshness threshold is stale. Collector disconnection never translates to device down. Enabled collector freshness scales with authorized inventory/worker capacity; clients must use the exposed threshold.
- `GET /api/v1/discovered?after=0&limit=100`: bounded discovery page; limit 1–200. `POST /api/v1/discovered/scan-now` is bodyless and limited to one request every 30 seconds. Discovery progress can report the `routes` phase. The scan response includes `upstreamLinks`, the number of router hints produced by that scan. `POST /api/v1/discovered/clear` is bodyless and removes all discovery records, not saved map devices. `POST /api/v1/discovered/:id/add-to-map` and `/remove` require the write header. Add-to-map JSON includes `baseRevision`; it returns `draft: {nodes, edges}` for review. Newly confirmed devices begin with monitoring disabled. Saved device types remain under editor control. Gateway routes are hints, not verified physical paths. Remove deletes only the discovery record. Discovery is opt-in; see DISCOVERY.md.
- A discovery row with a current switch-port match includes `switchPort: { switch, name }`. A proposed switch-port link includes the observation as an edge label in the returned draft patch.
- Discovery rows can have `source: "gateway"` for a default route observed during discovery or `source: "gateway-mac"` when another IP matches its hardware address. The page response includes `pendingCount` across all pages and a `pendingVersion` for those results. Admin-only `POST /api/v1/discovered/add-to-map` requires the write header and JSON with `baseRevision` and `pendingVersion`. It returns a batch draft patch and `addedCount` and `existingCount`. A changed inventory revision or set of pending results returns HTTP 409.
- `GET /api/v1/devices/:id/checks?limit=50&before=123`: `{checks:[{id:122,deviceId:"...",status:"up",checkedAt:"ISO UTC"}],nextBefore:...|null}`. Encode the stable device ID as a URL path component. Limit 1–200; before is a positive integer exclusive sequence cursor. Results are newest insertion first (sequence, not timestamp). Use nextBefore until null; inserts do not duplicate earlier pages. Deletions/retention may shorten later pages.

Snapshot responses carry a weak ETag. Send it in `If-None-Match` on the next request. An unchanged inventory, latest observation and incident state, collector, and discovery state produces HTTP 304 with an empty body. A 304 confirms connectivity without advancing individual check timestamps. The ETag also changes when a new host process starts.

The snapshot additionally includes `inventory` with the complete GET topology shape (`revision`, `updatedAt`, `topology`, `monitoring`), read in the same database transaction as observations. This additive field prevents a new address or deleted device from receiving evidence from a different inventory revision. Disabled devices display unknown health while retained history stays available. The UI ages checks locally against the freshness threshold with a clock offset derived from host timestamps. API failures preserve the last successful snapshot and timestamp.

`GET /api/v1/events` uses the same Host, Origin, fetch-site, loopback and remote session policy as `GET /api/v1/snapshot`. Remote viewers receive the same reduced projection on every event. The route sends no CORS headers and uses `Cache-Control: no-store`. Sessions are rechecked before sends and during idle periods. Logout, expiry, revocation, access being disabled, a role change, and host shutdown close the stream.

The stream sends `event: snapshot` with an opaque `id` and the full snapshot JSON in `data`. A shared 200 ms window coalesces changes and the snapshot version suppresses unchanged events. Every connection starts with the current full snapshot. If `Last-Event-ID` already matches the current snapshot, a `: resumed` comment precedes it. Missed intermediate versions are not replayed. A `: heartbeat` comment and `event: clock` with Unix milliseconds arrive roughly every 20 seconds to keep the stream open and refresh the clock offset. Limits are 32 streams per running host and four per client IP, with HTTP 429 and `Retry-After: 10` when full. HTTP/1.1 browsers typically allow roughly six connections per origin across tabs. The dashboard uses only one stream per visible tab and can fall back to short HTTP requests.

When mapped port evidence is available, snapshots include `uplinkStaleAfterMs` and `uplinkPorts` rows keyed by connection ID. A row may contain `source` and/or `target` values with `checkedAt`, `admin`, and `oper`. This excludes credentials, port descriptions, and unrelated ports. Port collection and authorization changes invalidate the snapshot ETag.

Snapshots with connections also include `linkHealth.links` and `linkHealth.redundancy`. Link entries carry `id`, endpoint objects (`deviceId`, `portLabel`, `checkedAt`, `fresh`, and optional `speedBps`), `state`, and evidence `scope`. Endpoint timestamps are host UTC. The last observed timestamp can remain present after evidence expires. State values are `unknown`, `oneSided`, `portsUp`, `forwarding`, `standby`, `down`, `mismatch`, and `degraded`. Scope values are `reachabilityOnly`, `snmpOneEnd`, `snmpBothEnds`, and `neighborVerified`. The host evaluates sampled port status, speed, and supported spanning tree evidence. Forwarding and standby require current port evidence. Neighbor verification is shown in discovery review. A sole port failure requires two distinct, consecutive samples. A fresh up/down disagreement is a mismatch immediately. Current observations cannot verify a port assigned to conflicting peers. Evidence expiry can change the ETag or emit a new SSE snapshot without another sample.

Each redundancy entry identifies the reviewed group and device with `id`, `deviceId`, `state` (`healthy`, `degraded`, `isolated`, or `unknown`), and `basis: "linkStatusOnly"`. Groups without a protected device retain their legacy summaries. Viewers receive the link and redundancy projections and the legacy inventory groups. Both roles receive `tiers` entries with a device ID and root-relative hop count, plus port speeds from fresh samples. Admins also receive root-relative structural `failurePoints`, the per-link `flapping` flag, and configuration fields including roots, roles, and baseline membership. Flapping uses three recent samples within one host run. Raw discovery evidence and collector diagnostics stay outside the link projection.

History additionally returns `revision`, read transactionally with checks; the dashboard rejects a page for a different selected inventory revision. Details fetch 25 rows at a time and display at most 200, with explicit refresh, error and empty states. Adjacent retained status changes are labelled without inferring continuity or uptime. Changing the selected device, inventory revision or latest check cancels obsolete requests and restarts from the newest page.

Host validation reuses the v1 validator: router/switch only, 2,000 devices, 10,000 links, unique IDs and canonical nonempty IP literals, existing distinct endpoints, labels 100 chars, descriptions 500, handle strings 100, finite coordinates. Additional host bounds: IDs 100 chars and coordinates ±10,000,000. Monitoring only accepts booleans for existing devices and requires a literal management address when true. Unknown rendering/status properties are stripped from topology. Inventory validation performs no DNS lookup or probe. Only the explicitly enabled Windows collector can probe opted-in literal addresses.

## Transport

HTTP is the loopback-only default. Set NETWATCH_TLS_CERT and NETWATCH_TLS_KEY to a matching PEM pair to enable direct HTTPS (TLS 1.2+), required for LAN sharing. The allow-list then accepts only HTTPS origins. The host adds Strict-Transport-Security and uses the Secure __Host-netwatch_session cookie only for HTTPS. The browser must trust the certificate and connect to the host directly. X-Forwarded-* headers are ignored. See [Remote access](REMOTE-ACCESS.md).

## Remote session API

Requests are admitted by the real socket peer. Loopback, RFC1918 IPv4, IPv6 link-local and IPv6 ULA peers qualify. IPv4-mapped peers are classified by their IPv4 address. Production binds only loopback and private IPv4 interfaces. Host must match a listener or configured hostname and port. If present, Origin must use the matching transport and an allowed authority, and Sec-Fetch-Site must be same-origin or none.

- GET /api/v1/auth/session returns authenticated, role, source, viewerMode and remoteEnabled. Authenticated remote sessions receive csrfToken and expiresAt. Open mode issues a viewer session here or on the SPA shell.
- POST /api/v1/auth/login accepts JSON with role and password. A successful login returns role, csrfToken and expiresAt and replaces the prior session. The cookie uses HttpOnly, SameSite=Strict and Path=/.
- POST /api/v1/auth/logout is bodyless. It invalidates the remote session and clears its cookie.

Remote admin writes require the session CSRF token in X-NetWatch-Write. Loopback writes retain the per-launch token. Remote protected requests without a session receive 401. Requests below the required role receive 403. Login backoff uses 429 and Retry-After. Admin sessions expire after 30 minutes idle or 12 hours absolute, with a limit of five. Viewer sessions expire after eight hours idle or seven days absolute, with a limit of 20. New sessions evict the oldest at each limit. All responses include Referrer-Policy, X-Frame-Options and Cross-Origin-Resource-Policy. API responses use Cache-Control: no-store.

## Access log

GET /api/v1/audit is loopback-only. It accepts limit (1–200, default 50) and before (an exclusive numeric ID). Results are {entries, nextBefore}, newest first. Entries contain id, at (Unix milliseconds), source, ip, role, action and detail. The audit log keeps at most 5,000 rows for up to 30 days and records fixed action names and outcomes. Passwords and tokens are excluded.

`GET /api/v1/audit/export` is loopback-only and downloads `netwatch-access-log.json`. It returns `{exportedAt,entries}` with up to 5,000 retained entries. Entries are restricted to the event timestamp, source, role and a recognized action. IP addresses and event details are excluded.

Stop the host and use the same NETWATCH_DB path as the launcher or host. Run npm run auth -- set-admin-password or npm run auth -- set-viewer-password in an interactive terminal. Passwords are entered twice without echo and must be distinct. Use npm run auth -- viewer-mode open (or password or disabled) to choose viewer policy, npm run auth -- status to inspect configuration, and npm run auth -- revoke-sessions to remove sessions. ## SQLite, migrations and retention

Schema v7 adds auth_config and sessions. The initial row requires a viewer password and has no password hashes. Backups can contain password hashes and should be protected like the live database. Restore clears sessions.

Schema v4 adds `snmp_targets` (non-secret device authorization identifiers) and `interface_samples` (latest sanitized IF-MIB results). The v3→v4 migration is transactional and preserves topology, checks and incidents; no devices or credentials are added implicitly. `GET /api/v1/devices/:id/interfaces?limit=50&after=<ifIndex>` returns `{revision,configured,checkedAt,uptime,total,interfaces,nextAfter,monitoring}`. Limit is 1–200; rows are ordered by numeric ifIndex. Monitoring contains fixed collector/attempt states and its independent stale threshold. Interface counters are decimal strings; rates are finite bits/second or null. The route shares existing loopback/Host/Origin protections and is read-only. There is no credential, interface-write or collection-trigger HTTP route. GET health also exposes the interface collector's safe readiness state.

`GET /api/v1/devices/:id/neighbors` is admin-only and returns the inventory revision, LLDP observation time when available, a state, up to 64 sanitized neighbor rows, and saved peers to choose from. `PUT` on the same path requires the write token, `baseRevision`, `checkedAt`, `neighborId` and an existing `peerId` or `peerId: null` with a label and type. Stale evidence or a changed map returns HTTP 409. A duplicate device pair returns `added: false`. Approved devices and links use the existing topology format.

Only a locally enrolled target can receive interface samples, with matching inventory revision and authorization. Latest storage is bounded to 512 interfaces/device and 20,000 globally; cap/malformed/probe errors retain prior evidence. Identity changes revoke SNMP authorization and remove its samples. Backups validate v4 interface bounds and rates; restore retains the observations but deliberately clears SNMP authorizations. Credentials remain in separate Windows CurrentUser DPAPI profiles and are not part of database/topology exports. See SNMP-INTERFACES.md for configuration and rate rules.

LLDP neighbor rows include `chassisMac` when the advertised chassis ID has the MAC address subtype. The neighbor review write returns a draft patch. The monitored inventory changes through the normal topology write.

The idempotent `checks_device_latest(device_id, checked_at DESC, seq DESC)` index supports sampling, retention and migration backfill. Snapshots read current observations from `latest_check` in one query. The latest observation advances even when a matching result is sampled out of check history.

Schema version uses SQLite user_version=14 with ordered transactional upgrades preserving inventory/history and adding bounded discovery records. See ICMP-COLLECTOR.md for new raw outcome, pending status and latency fields. Inventory (single revisioned record) and checks (indexed device, sequence and timestamp) are separate tables. Writes use BEGIN IMMEDIATE/COMMIT with rollback on failure. WAL and a three-second busy timeout support readers and serialize writers; one production host holds an exclusive filesystem lock directory. Observation batches are internal-only, max 2,000, validated against current explicit opt-in, optional expected inventory revision, finite latency and timestamps, and rolled back as a whole if any observation is invalid. Deleting a device or changing its address or type removes its old observations, including its latest result. Disabling monitoring retains history for the retention window.

Per-check history keeps roughly the most recent 5,000 stored checks per device. That covers about 3.5 days of stable one-minute samples and less when status or outcomes change often. Status, outcome and reason changes and outage transitions are always stored. A network-wide safety cap of 1,000,000 rows and a 30-day age ceiling can shorten that history. Retention runs at startup, after inventory writes and every ten minutes. Sample inserts enforce row caps immediately. History, incidents and snapshots use WAL read transactions. History pages return up to 200 rows. SQLite reuses freed pages, and offline backup compacts the file.

Initial schema creation and user_version are in one transaction. Migration failure exits without serving; the transaction rolls back and existing data is preserved. A newer schema is rejected rather than downgraded. Before opening an existing v1–v10 database with this host, stop NetWatch and use the existing backup command to create a file next to the database named `<database>.pre-v11.bak`. For a v11 database, use `<database>.pre-v12.bak`. For a v12 database, use `<database>.pre-v13.bak`. For a v13 database, use `<database>.pre-v14.bak`. For example, with `NETWATCH_DB` set to `C:\NetWatch\netwatch.sqlite`, run `npm run db -- backup "C:\NetWatch\netwatch.sqlite.pre-v11.bak"`. The host verifies SQLite integrity and matches the backup’s table data to the source before the first migration. A missing, invalid, or outdated backup blocks the upgrade. Keep prior backups under separate names. Fresh databases need no backup. After a migration error, stop all host processes, preserve the database and its WAL/SHM companions, fix the cause/use a compatible host, then retry. Do not delete a database to bypass a migration error.

## Database backup and restore

Stop the host, then:

```
npm run db -- backup /path/to/new-backup.sqlite
npm run db -- restore /path/to/backup.sqlite --confirm
```

On Windows use an accessible path such as `C:\NetWatchBackups\netwatch-2026-11-12.sqlite` and npm.cmd if necessary. Parent backup folders must already exist. Backups refuse to overwrite an existing file. VACUUM INTO makes a compact standalone SQLite backup; validate integrity, supported v1 through v14 schema, inventory and bounded history before accepting it. Restore validates the source before touching the target, stages a copy next to the target, checkpoints SQLite, then replaces the target file. Revision advances beyond both current and backup revisions so old browser writes are rejected. Back up the current database to a separate file before intentionally restoring; restore replaces its inventory/history.

The host and maintenance command share `<database>.lock`; concurrent maintenance is rejected. The directory records the owner PID, start timestamp and host in owner.json. A dead local PID or a missing/unreadable owner record in a directory older than 60 seconds lets NetWatch log and replace the stale lock. Running or inaccessible PIDs and records from another host still block acquisition. If a lock remains after an interrupted reclamation or contains unexpected files, confirm no host or maintenance process owns it before inspecting or removing it. If a restore is interrupted before replacement, the original remains; preserve any `.restoring` file, inspect it, and remove it only after confirming the host is stopped before retrying. Use verified backups for filesystem/disk failure recovery; this does not claim to recover arbitrary hardware corruption. Do not copy just an active WAL database's main file.

Automated tests cover restart persistence, independent-connection conflicts, inventory/observation rollback, migration failure/future version rejection, validation and origin/write limits, history pagination/retention/cap, backup/restore and corrupt backups. Browser checks cover explicit transfer, cancel, opt-in/import reset, conflict, load and responsive layouts. Windows process shutdown, file replacement and recovery still require actual Windows validation before release #16.

Windows 10 local validation now covers the real host startup, health/snapshot/history, restart persistence, offline backup, active helper cancellation and database lock release using only temporary databases and authorized loopbacks. Run `node scripts/check-windows-host.mjs --loopback` with the configured port free; see ICMP-COLLECTOR.md for the recorded results. Shutdown testing invokes the installed SIGINT handler via IPC; physical Ctrl+C delivery and broader crash/disk recovery remain release #16 checks.

## Local incidents (2.4)

Confirmed down observations open one incident per device in the same transaction as the check; repeated failures keep that incident open. A confirmed reachable/up observation resolves it once. The collector's two-failure/one-success policy debounces transient loss. Unknown/pending checks, process errors, disconnection and stale evidence cannot open or resolve incidents. A later confirmed outage creates a new incident. Older out-of-order checks do not change incident state.

GET /api/v1/snapshot includes activeIncidents (at most 2,000), each {id,deviceId,openedAt,resolvedAt:null}. GET /api/v1/devices/:id/incidents?limit=25&before=<id> returns {revision,incidents,nextBefore}, newest ID first, with resolvedAt an ISO timestamp or null. Limits are 1–200; cursors are positive integers. Both routes share existing Host/Origin protections. There is no incident-write or notification-configuration route.

Schema v3 adds incidents and a unique partial index enforcing one open incident per device. Migration creates an empty incident ledger rather than inventing historical transitions; the next confirmed down observation can open an incident. Restart preserves incidents; the collector still rebuilds consecutive failure streaks. Pausing monitoring preserves open incidents until a later confirmed recovery. Deletion or address/type replacement removes that identity's checks and incidents; label/layout edits preserve them.

Resolved incidents retain at most 30 days since recovery and 10,000 rows globally. Active incidents are retained until recovery or identity removal (bounded by the 2,000-device inventory). Age cleanup runs at startup, after inventory writes and every ten minutes. Recoveries enforce the resolved-incident cap immediately. Check retention is independent, so an old incident may outlive its supporting checks. Backup/restore validates and preserves the ledger. Notifications are in-app only: there are no external sends, credentials, retries or delivery configuration; external delivery remains deferred until an approved destination is provided.

## Topology discovery runs

- `GET /api/v1/discovery/runs` returns eligible seeds, the latest run, and current local connection hints. `POST /api/v1/discovery/runs` starts a run with JSON `{seedId}` and returns HTTP 202. One run can be active per host.
- `GET /api/v1/discovery/runs/:id` returns progress or saved proposals, normalized evidence, and fixed diagnostics. `POST /api/v1/discovery/runs/:id/cancel` is bodyless and leaves partial results.
- `POST /api/v1/discovery/runs/:id/accept` and `/reject` accept JSON `{baseRevision, ids}`. For acceptance, `preview: true` returns the draft patch while the proposals stay pending. An accepted IP suggestion includes `matches`, keyed by proposal ID with a saved device ID as its value. Accept returns a draft patch and records the review. The normal topology write applies the full draft after confirmation.
- `POST /api/v1/discovery/hints/:id/accept` returns a local connection hint as a draft patch. Review and cancellation are admin-only with write-token and CSRF checks. Viewer snapshots omit run data, candidate addresses, chassis keys, and raw proposal evidence.
- The run starts from one enrolled target, follows only individually enrolled routers and switches in scope, and uses each target's own protected profile. The default scope is directly attached RFC1918 and IPv6 ULA networks. `NETWATCH_LLDP_CIDRS` adds comma-separated private CIDRs. Loopback, link-local, multicast, and public addresses are excluded.
- Caps are 200 devices, eight hops, 512 neighbor rows per table, 2,000 proposal devices and 2,000 proposal links, and five minutes per run. `NETWATCH_LLDP_MAX_DEVICES`, `NETWATCH_LLDP_MAX_DEPTH`, `NETWATCH_LLDP_MAX_NEIGHBORS`, and `NETWATCH_LLDP_TIME_MS` can lower the corresponding run limits. Table reads have a separate 512-row ceiling. One discovery session runs at a time and yields to scheduled SNMP. Discovery uses a two-second SNMP timeout, one retry per request, and the existing request and deadline bounds.
- Up to ten runs and 512 local hints are stored. Hints are available for 24 hours. A run interrupted by a host restart is recorded as partial. The run store carries proposal decisions and supersedes older pending duplicates. Review and lifecycle audit records use fixed event names.

## Richer link evidence

Fresh endpoints may include `errorsPerSec`, `discardsPerSec`, and the derived `stp` state. Each rate sums the corresponding inbound and outbound counters for that endpoint. A physical input link in a recognized bundle may include `bundle: {total, up, state}`. For admin responses, `linkHealth.bundles` contains bundle representatives and member link IDs, and `link.role` is the role relative to its source endpoint. A specific manual role takes precedence over inference. Derived redundancy bases are `linkStatusOnly`, `stp`, `lacp`, and `stpAndLacp`.

Viewer link evidence includes only approved derived fields. Raw counters, protocol identifiers, CDP records, inferred role fields, bundle member lists, and administrative diagnostics stay outside that projection. The interface samples remain compatible with the existing Ports API.

The `interface_link_evidence` table holds an optional timestamp-matched row per enrolled device. Evidence expires with interface observations. Leaving the inventory or removing enrollment invalidates the row. Configure sustained thresholds using `NETWATCH_LINK_ERRORS_PER_SEC` and `NETWATCH_LINK_DISCARDS_PER_SEC`.

Admin discovery runs can include bounded CDP reports. Compatible reports identify the peer by matching management address plus device ID and match both port identifiers. The link proposal identifies corroboration with `sourceProtocol: "both"`. A CDP-only row remains advisory and grants no new target or credential access. ## Scheduled discovery and topology changes

Admins can save or disable a schedule with `POST /api/v1/discovery/schedule` and a JSON body containing `seedId` and `intervalMinutes`. A value of zero disables the schedule. Active intervals are 15 to 1,440 minutes and require an eligible enrolled seed. The schedule is disabled on a fresh database. Scheduled runs share the existing proposal review, enrollment limits, and single-running-job limit.

Admin HTTP and SSE snapshots include `dynamics.changes` and `dynamics.incidents`. Changes cover newly discovered devices and verified links, uniquely identified port moves, links absent across two eligible complete runs, and negotiated speed changes. The first complete run establishes a baseline per seed. The change feed returns up to 50 entries from the last 30 days. Incident data returns up to 100 active and recently resolved entries, with state, opening and resolution times, and the downstream device count. Viewer projections and validators exclude these fields and the associated update version.
